## 1. Введение 

### 1.1 Назначение документа

SDD описывает архитектуру и проектные решения настольного агрегатора оповещений версии 1.0 и служит руководством для разработчиков, реализующих ядро на C++ и графический интерфейс, а также для сопровождающего персонала и заказчика, оценивающего соответствие продукта требованиям. Документ уточняет, как система реализует требования SRS, и дополняет SRS, не заменяя его. 
### 1.2 Область применения 

Проектируемая система — «Агрегатор оповещений» версии 1.0: настольное приложение с графическим интерфейсом, которое принимает оповещения от источников трёх типов (проверяемые сервисы, сервис погоды, источник сетевых аномалий), приводит их к единому формату, объединяет дубли, присваивает уровень критичности и показывает пользователю единый список с уведомлениями и журналом подтверждений. Входит в область SDD: ядро обработки оповещений, локальное хранилище, графический интерфейс, контроль доступности источников и изоляция сбоев. Не входит: отправка во внешние каналы (почта, SMS, мессенджеры), подключение к оборудованию по SNMP/syslog, корреляция событий между источниками, эскалация по времени, многопользовательская работа и авторизация — эти функции исключены ограничениями п. 2.3 SRS. Источники погоды и сетевых аномалий в учебной версии могут быть заменены имитаторами.

### 1.3 Определения, акронимы и сокращения 

| Term | Definition |
|------|------------|
| ADR | Architectural Decision Record — запись архитектурного решения |
| API | Application Programming Interface — набор определений и протоколов для интеграции прикладного ПО |
| SRS | Software Requirements Specification — спецификация требований к ПО |
| SDD | Software Design Document — документ описания дизайна ПО |
| Оповещение | Сообщение источника о событии, требующем внимания пользователя |
| Источник | Внешний по отношению к ядру поставщик оповещений: проверяемый сервис, сервис погоды или источник сетевых аномалий |
| Уровень критичности | Степень важности оповещения: «информационный», «предупреждение», «критический» |
| Дубликат | Оповещение с теми же источником, типом и описанием, что у активного оповещения |
| Активное оповещение | Оповещение, прочтение которого ещё не подтверждено |
| Канонический ключ | Кортеж (источник, тип, описание), используемый для поиска дубликата |

## 2. Обзор дизайна 

### 2.1 Задачи стейкхолдеров 

| Стейкхолдер | Основные задачи (concerns) | Адресующие точки зрения / элементы |
|-------------|----------------------------|-------------------------------------|
| Пользователь-наблюдатель | Единый список, упорядочивание и фильтрация, уведомления о критических, подтверждение прочтения (BR-01, BR-03, BR-04, BR-05) | Контекст, Интерфейс, Взаимодействие |
| Администратор | Добавление/отключение источников, периодичность опроса, правила критичности (REQ-FUNC-001, REQ-FUNC-004) | Композиция, Интерфейс, Динамика состояний |

| Разработчик | Модульность, локализация ответственности, тестируемость (REQ-FUNC-002…007, REQ-REL-008/009) | Композиция, Логическое представление, Зависимости, Алгоритм |
| Сопровождающий персонал | Изоляция сбоев, журналирование, локальное хранение (REQ-REL-009) | Взаимодействие, Динамика состояний, Информация |

#### 2.1.1 Приоритеты функционала

Приоритеты функционала установлены по шкале от 10 (Critical — максимальный приоритет) до 50 (Low Priority — минимальный приоритет) в соответствии с результатами планирования и согласования с заказчиком (см. отчёт по лабораторной работе №4, раздел 2.2).

| Приоритет | Описание функционала | Связанные требования |
|-----------|----------------------|----------------------|
| 10 (Critical) | Приём оповещений от настроенных источников и приведение их к единому формату | REQ-FUNC-001, REQ-FUNC-002 |
| 20 | Объединение повторяющихся оповещений и присвоение уровня критичности по правилам администратора | REQ-FUNC-003, REQ-FUNC-004 |
| 30 | Единый список оповещений с упорядочиванием и фильтрацией по источнику и уровню критичности | REQ-FUNC-005 |
| 40 | Уведомление о критических оповещениях и подтверждение прочтения с ведением журнала | REQ-FUNC-006, REQ-FUNC-007 |
| 50 (Low Priority) | Контроль доступности источников с ограничением ожидания 10 с и изоляцией сбоев | REQ-REL-008, REQ-REL-009 |

**Пояснение к шкале.** Значение 10 соответствует критически важному функционалу, без которого система не выполняет своё назначение; значение 50 — функционалу минимальной приоритетности, который может быть отложен без ущерба для базовой работоспособности версии 1.0. Приоритеты используются при планировании итераций и при разрешении конфликтов объёма работ (trade-off) в случае изменения требований.

### 2.2 Выбранные точки зрения 

Для адресации задач стейкхолдеров выбраны следующие точки зрения: **Контекст** (границы и акторы), **Композиция** (декомпозиция ядра и UI), **Интерфейс** (контракты модулей и источников), **Взаимодействие** (сценарии приёма, дедупликации, уведомления, таймаута), **Динамика состояний** (жизненный цикл оповещения и состояние источника), **Зависимости** (направленные связи модулей). Точки зрения «Физическое представление», «Параллелизм» и «Ресурсы» раскрыты кратко, поскольку система настольная и однопользовательская.

#### 2.2.1 Контекст 

**Адресует**: границы системы, акторы окружения, предоставляемые сервисы (REQ-FUNC-001, BR-01, BR-06).
**Язык**: контекстная диаграмма C4 / диаграмма вариантов использования UML (см. `sysml/aggregator-context.sysml`).

Акторы: Пользователь-наблюдатель, Администратор (в учебной версии может совмещаться), Заказчик. Внешние системы: проверяемые сервисы, сервис погоды (или имитатор), источник сетевых аномалий (журнал событий или имитатор). Система предоставляет: приём оповещений, единый список, уведомления, подтверждение прочтения, контроль доступности источников. Внешние каналы доставки (почта, SMS, мессенджеры) в границы не входят.

#### 2.2.2 Композиция 

**Адресует**: выявление основных элементов дизайна, распределение ответственности, модульность (REQ-FUNC-001…007, REQ-REL-008/009, REQ-CON-010).
**Язык**: диаграмма компонентов UML / иерархическая декомпозиция.

**Функциональная (логическая) декомпозиция:**
- `SourceAdapter` — адаптеры источников трёх типов (опрос сервисов, API погоды/имитатор, журнал/имитатор аномалий).
- `Normalizer` — приведение к единому формату (REQ-FUNC-002).
- `Deduplicator` — объединение дублей по каноническому ключу (REQ-FUNC-003, ADR).
- `SeverityEngine` — присвоение уровня критичности по правилам администратора (REQ-FUNC-004).
- `AlertRepository` — локальное хранилище активных оповещений и журнала (REQ-FUNC-007).
- `AlertListController` — список, упорядочивание и фильтрация (REQ-FUNC-005).
- `NotificationController` — уведомление о критических оповещениях (REQ-FUNC-006).
- `SourceHealthMonitor` — контроль доступности и таймаут 10 с (REQ-REL-008), изоляция сбоев (REQ-REL-009).
- `MainWindow` / `ModalDialog` — графический интерфейс (см. `mockups/`).

**Рантайм (физическая) декомпозиция:** единый процесс настольного приложения; фоновый поток опроса источников; поток UI; локальное хранилище на диске.

#### 2.2.3 Логическое представление 

**Адресует**: статические абстракции и их реализации (REQ-FUNC-002, REQ-FUNC-003, REQ-FUNC-004).
**Язык**: диаграмма классов UML.

Ключевые типы: `Alert` (источник, тип, уровень критичности, время возникновения, описание, счётчик повторений, время последнего повторения, признак подтверждения), `SeverityRule` (условие → уровень), `SourceConfig` (имя, тип, способ получения, периодичность), `DeduplicationKey` (источник + тип + описание). `Alert` инкапсулирует инвариант «ровно один уровень критичности» (REQ-FUNC-004).

#### 2.2.4 Физическое представление 

**Адресует**: материальная инфраструктура (ограничение п. 2.3 SRS — настольное приложение).
**Язык**: структурная схема.

Один компьютер пользователя; локальный диск для хранения оповещений и журнала; сеть — только для опроса проверяемых сервисов и получения данных погоды при подключении реального сервиса.

#### 2.2.5 Структура 

**Адресует**: внутренняя организация компонентов и коннекторов (REQ-FUNC-001, REQ-REL-009).
**Язык**: диаграмма композитной структуры UML.

`SourceAdapter` предоставляет порт `fetch()`, через который `SourceHealthMonitor` инициирует опрос с таймаутом 10 с; результат передаётся в `Normalizer` через коннектор «сырое оповещение → единый формат». Сбой одного адаптера изолируется на уровне порта и не затрагивает остальные (REQ-REL-009).

#### 2.2.6 Зависимости 

**Адресует**: связанность и анализ влияния изменений (REQ-CON-010, REQ-REL-009).
**Язык**: граф зависимостей / диаграмма пакетов UML.

Направленные зависимости: `MainWindow` → `AlertListController` → `AlertRepository`; `SourceAdapter` → `Normalizer` → `Deduplicator` → `SeverityEngine` → `AlertRepository`; `NotificationController` ← `AlertRepository`; `SourceHealthMonitor` → `SourceAdapter`. Зависимости направлены «вниз» к хранилищу; UI не зависит от адаптеров напрямую (изоляция сбоев, REQ-REL-009).

#### 2.2.7 Информация 

**Адресует**: структура данных, постоянное хранение, целостность (REQ-FUNC-002, REQ-FUNC-007).
**Язык**: диаграмма «сущность-связь» / логическая модель данных.

Сущности: `Alert` (активные и подтверждённые), `SourceConfig`, `SeverityRule`, `EventLog` (журнал ошибок и подтверждений). Хранение локальное; подтверждение прочтения сохраняется после перезапуска (REQ-FUNC-007). Наименования согласованы с точкой зрения Logical.

#### 2.2.8 Интерфейс 

**Адресует**: контракты между модулями и с источниками (REQ-FUNC-001, REQ-FUNC-006).
**Язык**: сигнатуры функций/методов, спецификации API.

Контракты: `SourceAdapter::fetch(timeout=10s) → RawAlert | TimeoutError`; `Normalizer::normalize(RawAlert) → Alert` (отклоняет при отсутствии обязательного поля, REQ-FUNC-002); `Deduplicator::upsert(Alert) → Alert` (обновляет счётчик, REQ-FUNC-003); `SeverityEngine::assign(Alert) → Severity` (при отсутствии правила — «информационный», REQ-FUNC-004); `NotificationController::notify(Alert) → void` (≤ 5 с для критических, REQ-FUNC-006).

#### 2.2.9 Взаимодействие 

**Адресует**: распределение ответственности, порядок сообщений, распространение ошибок (REQ-FUNC-003, REQ-FUNC-006, REQ-REL-008, REQ-REL-009).
**Язык**: диаграмма последовательности UML.

Сценарии: (1) «счастливый путь» — опрос → нормализация → дедупликация → критичность → сохранение → уведомление; (2) «дубликат» — 10 повторов дают одну запись со счётчиком 10 (REQ-FUNC-003); (3) «таймаут» — источник не ответил за 10 с → статус «недоступен» ≤ 11 с (REQ-REL-008); (4) «сбой источника» — ошибка записывается в журнал, остальные источники продолжают обновляться (REQ-REL-009). Для каждого сценария приведены репрезентативные «путь отказа».

#### 2.2.10 Алгоритм 

**Адресует**: логика дедупликации и присвоения критичности (REQ-FUNC-003, REQ-FUNC-004).
**Язык**: псевдокод.

Алгоритм дедупликации (ADR): ключ = (источник, тип, описание); если активное оповещение с ключом существует — обновить время последнего повторения и увеличить счётчик; иначе создать новую запись. Алгоритм присвоения критичности: перебор правил администратора; при отсутствии подходящего — «информационный». Привязка к `Deduplicator` и `SeverityEngine`.

#### 2.2.11 Динамика состояний 

**Адресует**: состояния оповещения и источника (REQ-FUNC-007, REQ-REL-008).
**Язык**: диаграмма конечных автоматов UML.

Оповещение: `Активное → Подтверждённое` (по подтверждению прочтения, REQ-FUNC-007); подтверждённое выпадает из дедупликации. Источник: `Доступен → Недоступен` (по таймауту 10 с, REQ-REL-008) → `Доступен` (после ответа). Диаграмма дополняет Interaction при поведении, зависящем от состояния.

#### 2.2.12 Параллелизм 

**Адресует**: структура потоков и синхронизация (REQ-REL-009, REQ-FUNC-005).
**Язык**: диаграмма активности UML.

Фоновый поток опроса источников и поток UI; доступ к `AlertRepository` синхронизирован (мьютекс/очередь сообщений), чтобы интерфейс оставался отзывчивым при сбое источника (REQ-REL-009) и фильтрация 1000 записей укладывалась в ≤ 1 с (REQ-FUNC-005).

#### 2.2.13 Паттерны 
**Адресует**: повторное использование проверенных решений.
**Язык**: диаграмма классов/пакетов UML.

Применены: Adapter (`SourceAdapter` для трёх типов источников), Repository (`AlertRepository`), Observer (UI подписывается на обновления списка), Strategy (правила критичности `SeverityRule`). Паттерны зафиксированы с указанием места применения.

#### 2.2.14 Развёртывание 

**Адресует**: отображение компонентов на узлы (ограничение п. 2.3 SRS).
**Язык**: диаграмма развёртывания UML.

Один узел — компьютер пользователя; артефакт — исполняемый файл настольного приложения; локальное хранилище на диске. Внешние узлы: проверяемые сервисы и сервис погоды (по сети, при подключении реального сервиса).

#### 2.2.15 Ресурсы 

**Адресует**: использование ограниченных ресурсов (REQ-REL-008, REQ-FUNC-005).
**Язык**: таблица распределения ресурсов.

Таймаут опроса — 10 с на источник (REQ-REL-008); поток опроса — один фоновый поток; хранилище — локальный диск; целевое время фильтрации 1000 записей — ≤ 1 с (REQ-FUNC-005). Перекрёстные ссылки на Concurrency и Deployment.

## 3. Проектные представления 

- **ID**: 001-Контекст
- **Title**: Границы агрегатора и акторы окружения
- **Viewpoint**: Контекст
- **Representation**: контекстная диаграмма C4 (см. `sysml/aggregator-context.sysml`): акторы — наблюдатель, администратор, заказчик; внешние системы — проверяемые сервисы, сервис погоды/имитатор, источник аномалий/имитатор; система предоставляет приём, список, уведомления, подтверждение, контроль доступности.
- **More Information**: реализует REQ-FUNC-001, BR-01, BR-06; см. ADR по дедупликации.

- **ID**: 002-Композиция ядра
- **Title**: Декомпозиция ядра обработки оповещений
- **Viewpoint**: Композиция
- **Representation**: диаграмма компонентов: `SourceAdapter` → `Normalizer` → `Deduplicator` → `SeverityEngine` → `AlertRepository`; `AlertListController`, `NotificationController`, `SourceHealthMonitor`, `MainWindow`.
- **More Information**: реализует REQ-FUNC-001…007, REQ-REL-008/009; см. решения 001 (дедупликация) и 002 (изоляция сбоев).

- **ID**: 003-Интерфейс источников
- **Title**: Контракт адаптера источника с таймаутом
- **Viewpoint**: Интерфейс
- **Representation**: сигнатура `SourceAdapter::fetch(timeout=10s) → RawAlert | TimeoutError`; `Normalizer::normalize(RawAlert) → Alert` с отклонением при отсутствии обязательного поля.
- **More Information**: реализует REQ-FUNC-001, REQ-FUNC-002, REQ-REL-008.

- **ID**: 004-Взаимодействие при дедупликации
- **Title**: Последовательность объединения повторяющихся оповещений
- **Viewpoint**: Взаимодействие
- **Representation**: диаграмма последовательности: 10 повторов → `Deduplicator::upsert` обновляет счётчик → одна запись со счётчиком 10.
- **More Information**: реализует REQ-FUNC-003, BR-02, BG-3; см. решение 001.

- **ID**: 005-Динамика состояний оповещения
- **Title**: Жизненный цикл активного и подтверждённого оповещения
- **Viewpoint**: Динамика состояний
- **Representation**: конечный автомат `Активное → Подтверждённое`; подтверждённое исключается из дедупликации.
- **More Information**: реализует REQ-FUNC-007; связано с решением 001 (последствие о подтверждённых оповещениях).

- **ID**: 006-Зависимости модулей
- **Title**: Направленные зависимости ядра и UI
- **Viewpoint**: Зависимости
- **Representation**: граф зависимостей `MainWindow → AlertListController → AlertRepository`; `SourceAdapter → Normalizer → Deduplicator → SeverityEngine → AlertRepository`; UI не зависит от адаптеров напрямую.
- **More Information**: реализует REQ-REL-009, REQ-CON-010; см. решение 002.

## 4. Решения 

- **ID**: 001-Дедупликация
- **Title**: Объединение повторяющихся оповещений через канонический ключ (источник + тип + описание)
- **Context**: повторные опросы недоступного сервиса порождают одинаковые оповещения; BR-02/BG-3 требуют 10 → 1 запись со счётчиком 10; REQ-FUNC-003 задаёт критерий дубликата.
- **Options**: канонический ключ с хеш-таблицей активных оповещений; полное побайтовое сравнение; ручное объединение пользователем.
- **Outcome**: выбран «канонический ключ с хеш-таблицей активных оповещений», потому что напрямую реализует REQ-FUNC-003, обеспечивает поиск O(1) в среднем (укладывается в REQ-FUNC-005) и не меняет единый формат (REQ-FUNC-002).
- **More Information**: полный ADR — в `adr-template.md` (заполненный); последствия: требуется правило разрешения конфликта критичности; подтверждённые оповещения выпадают из дедупликации (REQ-FUNC-007).

- **ID**: 002-Изоляция сбоев
- **Title**: Изоляция сбоя источника на уровне адаптера и фонового потока
- **Context**: REQ-REL-009 требует, чтобы сбой одного источника не нарушал работу остальных и интерфейса; REQ-REL-008 задаёт таймаут 10 с.
- **Options**: изоляция на уровне адаптера с таймаутом и записью в журнал; общий цикл опроса без изоляции; перезапуск приложения при сбое.
- **Outcome**: выбрана «изоляция на уровне адаптера с таймаутом и записью в журнал», потому что она удовлетворяет REQ-REL-008/009 и сохраняет отзывчивость интерфейса.
- **More Information**: см. представления 003 и 006; связано с решением 001.

## 5. Приложения 

- **Схема потока обработки**: источники (сервисы, погода, аномалии) → `Normalizer` → `Deduplicator` → `SeverityEngine` → `AlertRepository` → `AlertListController` / `NotificationController`.
- **Перечень источников**: имя, тип, способ получения (опрос, API, журнал, имитатор), периодичность опроса.
- **Графическая часть**: `sysml/aggregator-context.sysml`, `sysml/aggregator-ui.sysml`, прототипы экранов в `mockups/`.
- **Трассировка требований**: REQ-FUNC-001…007, REQ-REL-008/009, REQ-CON-010 — см. раздел 3 (представления) и раздел 4 (решения).
